# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm install`: install dependencies. Node.js `>=22.18.0` is required: Node runs the server's TypeScript directly and provides its SQLite database.
- `npm run dev`: the game with hot reload (http://localhost:5173). It forwards `/api` requests to port 3000, so run `npm run server` in a second terminal to play online. Without the server, only "Jouer sans compte" works.
- `npm run server`: the game server on port 3000, restarting on code changes. Its database is `data/royaume.db`, which git ignores.
- `npm start`: production server, with the API plus the built game from `dist/` (run `npm run build` first). Environment variables: `PORT`, `DATABASE_FILE`, `STATIC_DIR`.
- `npm test`: run the tests once (Vitest), covering the game rules and the server. `npm run test:watch` re-runs them on save.
- `npx vitest run server/app.test.ts -t "<test name>"`: run a single test.
- `npm run simulation` (or `npm run simulation -- orcs 7` for another race and seed): a virtual player (`scripts/simulation.ts`) follows the objective chain from a new game and prints the game time each objective takes, or where it gets stuck. Run it after balancing changes in `config.ts`; it depends on balancing values, so it is not a test.
- `npm run build`: type-check (`npm run typecheck`: `vue-tsc` for the client, `tsc -p tsconfig.server.json` for the server, the rules and `scripts/`), then build the game into `dist/`. There is no linter yet.

npm 10 can crash with `Cannot read properties of null (reading 'edgesOut')` when it resolves the dev dependencies from scratch (vitest's optional peers), for example when adding a package. `npm install --legacy-peer-deps` works around it. Installing from the existing `package-lock.json` is unaffected.

## Architecture

A Vue 3 + TypeScript + Vite single-page app with a French UI, plus a Node.js server (Hono and SQLite) that holds player accounts and their games. Roadmap steps 1 and 2 are implemented: the city, troops, heroes and research, and a live map of the surroundings where the player commands armies, fights timed battles against monster camps and patrolling monster bands, and gathers resources. Monster raids march on the city, which its troops and the Remparts defend. Both maps (the city and its surroundings) can be panned and zoomed. Step 3 is under way: accounts and online games work. For now the owner develops with a local server; hosting comes later.

- `src/game/` holds the game rules in plain TypeScript, with no Vue, DOM or browser-storage dependency. Both the browser and the server run this code, so keep it that way. Node runs these files directly by stripping their types. Imports inside `src/game/` and `server/` therefore keep their `.ts` extension, and only erasable TypeScript is allowed: no `enum`, no parameter properties (`tsconfig.server.json` enforces this).
  - `config.ts` holds every number: resources, races and their bonuses, buildings, troops (the four `Family` units plus one unit per race, with its `family` and `race`, and what each one carries, `load`), heroes (`HEROES`: recruitment, skills and their `SkillEffect`, the XP curve), monsters (including the XP each one gives) and camps, quests (`QUESTS`: goals, rewards, and an optional `gift` such as the dragon egg), the dragon (`DRAGON_*`: hatching cost and time, attack, health and growth, XP curve, rest, upkeep), spells (`SPELLS`: effect, Tour des mages level, cost, duration), monster bands (kinds, growth per level, levels by distance, aggro radius, spawn timing, patrols), raids and the city's defence (`RAID_*`: start, interval, speed, size, gates, plunder, respite; `WALL_*`: guards and health bonus; `PROTECTED_PER_CASTLE_LEVEL`, `SIEGE_*`), resource nodes (`NODE_KINDS`: amounts, gather rates, spawn timing), costs, durations, production, growth factors and the starting state. It also holds the world map geometry (`WORLD`, camp positions, `BAND_SPOTS`, `NODE_SPOTS`, `RAID_GATES`) and the pace of the world (`MARCH_SPEED`, `PATROL_SPEED`, `RAID_SPEED`, `WORLD_TICK_SECONDS`, `BATTLE_ROUND_SECONDS`), because the rules move armies and bands on the map. Balancing changes go here, not in the rules.
  - `rules.ts` is pure functions over an immutable `GameState`. When food is empty and upkeep exceeds production, troops are starving (`isStarving`): nobody deserts, but battle rounds played while starving apply `STARVATION_ATTACK_MALUS` to the attackers. `constructions` holds up to `maxConstructions` builds (one, then two from `SECOND_CONSTRUCTION_CASTLE_LEVEL`), never two on the same building (`constructionOf`). `trainings` holds at most one training per troop type, so the types train in parallel; a race unit can only be trained by its race (`checkTraining`). Research effects are data in `TECHS` (`TechEffect` kinds) and are read through `techBonus(state, kind, resource?)`, which production, durations, battles, march speed and army slots all use. Players can dismiss troops (`dismissTroops`) to cut upkeep, which also avoids a soft-lock (no food means no Château upgrade, which caps the farms). Each player action (`startUpgrade`, `startResearch`, `startTraining`, `recruitHero`, `learnSkill`, `claimQuest`, `castSpell`, `startMarch`, `orderArmy`, `dismissTroops`) advances first, then validates with its `check*` function, which returns the reason shown in the UI.
    - Time: nothing runs in the background. `advance(state, now)` replays everything up to `now` in time order, accruing net production (production minus troop food upkeep, never below zero) up to each step. Scheduled events happen at their exact time (`nextEvent`: construction, research, training and spell ends, band, node and raid spawns, raid arrivals). While something can happen outside the city, the world also moves in ticks (`worldTick`, one per `WORLD_TICK_SECONDS`): due battle rounds are played, armies march, gather or arrive, then bands check their aggro zones. Ticks fall on absolute multiples of the tick length (`tickedAt` holds the last one), and an event at the same instant comes first, so advancing in one jump or second by second gives the same result (a test checks it). This is what makes offline progress work. When nothing can happen (`worldIsQuiet`: no battle, and either no army outside or every army idle out of reach of every patrol with no raid on the map), there are no ticks, so a week offline stays cheap. `advance` throws after 10 000 steps at the same instant rather than loop forever.
    - Armies: `state.armies` holds the armies outside the city (`FieldArmy`: troops, position, `order`, `status`, `load`, `fought`), up to `maxArmies` (1 + the Commandement tech). `startMarch` sends a new army out of the city with a first order, and `orderArmy` gives an army a new one at any time (it retreats first if it is fighting). An order is a `Target`: a point, a camp, a band or a resource node (by id), or the city. Armies march in straight lines at `marchSpeed`. At a point, they wait (`idle`); at a camp or a band, they fight; at a node, they gather; at the city, they disband and add their `load` to the reserves.
    - Heroes: `state.heroes` holds the recruited heroes (`Hero`: level, xp, skill levels). A hero leads at most one army (`FieldArmy.hero`, `heroArmy`) and is free again when the army disbands or falls. `heroBonus(state, hero, kind, family?)` sums its skill effects, which apply to that army only: attack and family attack in `battleStacks`, health in the battle's `healthFactor`, march speed (`marchSpeed(state, hero)`, `marchDuration`), gathering (`gatherRate`) and load (`carryCapacity`). `endBattle` gives the hero XP for each monster defeated, whatever the outcome (`gainXp`, `xpToNextLevel`); each level brings a skill point (`skillPoints`).
    - Spells: `state.spells` holds the spells at work, each until its `endsAt`, when a scheduled event removes it (so production changes at the exact time). `spellBonus(state, kind, resource?)` adds their effects to production (`buildingOutput`), attack (`battleStacks`), health (at battle start) and march speed. The Tour des mages level unlocks them, and a spell cannot be cast again while it works (`checkCast`, `castSpell`).
    - Quests: `QUESTS` form a chain. `currentQuest` is the first one not yet claimed (`state.quests` lists the claimed ones), and only it can be claimed, once `questDone` (`checkClaim`, `claimQuest`). `questProgress` reads each goal from the state; what the state cannot recompute is counted in `state.stats` (victories, bands defeated, raids repelled and victories per camp, `campsDefeated`, in `endBattle` and `endSiege`, resources gathered in `gather`).
    - Battles: `state.battles` holds the battles in progress, with one round every `BATTLE_ROUND_SECONDS` (`playRound` calls `fightRound`, and health carries over between rounds). Each round, a side loses at most `1 / MIN_BATTLE_ROUNDS` of its starting health (`battleCaps`, from the battle's `sent`, `enemies`, `healthFactor` and guards), so a battle lasts at least `MIN_BATTLE_ROUNDS` rounds. `battleHealth` gives each side's starting and current health (troops plus wall guards, monsters), which the caps and the health bars on the maps use. A battle ends when a side falls (`victory` or `defeat`), when the player retreats (`retreat`) or after `MAX_BATTLE_ROUNDS` (`draw`). `endBattle` writes the `BattleReport` (`outcome`, `ambush`, `rounds`, and `foe`: a camp, or a band's kind and level) and the hero's `HeroGain`, and puts victory loot in the army's `load`. An army attacked on the way then resumes its order; otherwise it waits where it stands.
    - Bands: `state.bands` patrol an octagon loop (`patrolLoop`, `PATROL_RADIUS`) around their `home`. `bandPosition` derives a band's position from `phase`, `since` (null while it fights) and `direction`, so bands need no per-tick state. `checkAggro` starts an ambush when an army comes within `aggroRadius` of a band, unless the band is in the army's `fought` list. Bands spawn as scheduled events (`nextBandAt`, `null` when the map is full) on free `BAND_SPOTS`, never within reach of an army. The spot, the level (from distance, sometimes one more), the kind, the starting phase and the direction are drawn with `random(state.seed)`. That generator is seeded from the state, so the browser, the server and replays all agree.
    - Raids: a raid is a `Band` with `raid: true`. It walks from its `home` (one of `RAID_GATES`, drawn at random) straight to the city at `RAID_SPEED`, so `phase` is the distance walked and `raidArrival` gives its arrival time, a scheduled event. Raids do not count towards `MAX_BANDS` (`patrolCount`) and free no band spot when they go. `nextRaidAt` is null until a Château upgrade reaching `RAID_CASTLE_LEVEL` completes (`finishConstruction`), then `spawnRaid` schedules the next one every `RAID_INTERVAL_SECONDS`; the raid level follows the Château (`raidLevel`), with `raidMonsters` and `raidLoot` scaled by `RAID_SIZE`. Armies can target or meet a raid like any band (an interception counts in `raidsRepelled`). At the city, `startSiege` opens a `Battle` with `army: null` and a `siege` (`Siege`: the wall guards, `wallGuards`, as one more attacker stack in `battleStacks` and `playRound`); the city's troops fight, with `WALL_HEALTH_PER_LEVEL` more health. Only one siege runs at a time (`siegeOf`); a raid arriving meanwhile waits `SIEGE_WAIT_SECONDS` at the gates. During a siege, troops can neither leave nor be dismissed. `endSiege` heals `SIEGE_HEALED_SHARE` of the fallen, puts the raid's loot straight into the reserves on a victory, or takes `plunderOf` on a defeat (`RAID_PLUNDER_SHARE` above `protectedAmount`, capped by what the surviving monsters carry) and pushes `nextRaidAt` back by `RAID_RESPITE_SECONDS`; the raid leaves in every case. Its report has `army: null` and a `siege` (`SiegeReport`: guards, guards lost, healed troops, plunder).
    - Dragon: `state.dragon` is null until a quest with `gift: 'dragonEgg'` is claimed, then holds the egg (`stage: 'egg'`). `hatchEgg` (needs the Aire du dragon, `dragonRoost`) pays `DRAGON_HATCH_COST` and sets `hatchAt`, a scheduled event after which the dragon is `grown`. Its `xp` grows like a hero's, and `dragonLevel` derives its level from it (`dragonXpForLevel`), never above the Aire's level; `dragonAttack` and `dragonHealth` follow. `startMarch` takes it along with `dragon: true` (`FieldArmy.dragon`, `checkDragon`: one army at a time, with at least one troop, not while it rests). In a battle, `Battle.dragon` (`battleDragon`: attack, starting and current health) is one more attacker stack after the wall guards, with the army's attack bonuses and health factor; at home, it also defends the city in sieges (`dragonAtHome`). `dragonAfterBattle` gives it the same XP as a hero; if it fell (`BattleRound.dragonFell`), it leaves the army and rests until `restUntil` (`dragonResting`). It eats `DRAGON_UPKEEP_PER_LEVEL` per level in `upkeepPerHour`. Reports carry its `DragonGain`.
    - Resource nodes: `state.nodes` (`ResourceNode`: resource, level, position, `remaining`) spawn the same way (`nextNodeAt`, `NODE_SPOTS`). Only one army at a time can gather a node (`nodeGatherer`). Each troop gathers its resource's `gatherRate` per second. The army heads home by itself when it is full (`carryCapacity`, from each unit's `load`) or when the node runs out, and an empty node disappears.
    - Helpers: `targetPosition` takes a time, because bands move. `bandsNearPath` lists the patrols near a path, for warnings, and `patrolDistance` gives the exact closest distance between a patrol and a point. `distance` uses `Math.sqrt`, not `Math.hypot`, whose results can differ between JavaScript engines.
  - `actions.ts` turns player orders into data (`Action`: upgrade, research, train, dismiss, recruit, skill, claim, cast, hatch, march with an optional hero and dragon, order). `performAction(state, action, now)` advances, checks and applies an order, and returns the refusal reason if it is impossible. `parseAction` validates untrusted JSON (known ids, integer counts, targets inside the map, no other fields) before the server uses it.
  - `save.ts`: `restoreState` rebuilds a stored game field by field, defaulting what older saves lack and dropping fields the game no longer has. The browser save and the server database both go through it, so a new state field must get its default there. It also upgrades older saves: armies from before map orders (`expeditions`) come home with their troops and loot, motionless bands start patrolling around where they stood, and old reports get an `outcome`. Games from before heroes get `heroes: []`, and their armies `hero: null`. Games from before raids get `raid: false` bands, `siege: null` battles and reports, and a first raid five minutes later if their Château is already big enough. Games from before the dragon get `dragon: null`, armies `dragon: false`, battles and reports `dragon: null`, and empty `campsDefeated`. Armies and battles from before race units get zero counts for the new troop types. A single `construction` from older saves becomes `constructions`, and older games start with empty `stats`, no claimed quests and no spells.
  - `battle.ts` is the deterministic battle simulation: simultaneous rounds, damage spread across the enemy groups by head count, and a bonus against the family named in `strongAgainst`. A round deals only `BATTLE_DAMAGE_SCALE` of each fighter's attack, and `fightRound` takes optional `caps` (`roundCap`: a share of a side's starting health) that limit what each side loses in one round; both slow battles down without changing who wins. Stacks carry a `Family`: monsters, and race units (`UnitDef.family`), fight with the strengths of one of the four families. `fightRound` plays one round on health pools and returns its log (damage and losses), which the rules keep in the battle's `rounds` for the combat log; `fight` plays a whole battle at once.
  - The tests (`*.test.ts`) avoid depending on balancing values: they build states with unlimited resources, or groups with fixed stats. `richGame` has no bands, no nodes and no raids; `withBand`, `withRaid` and `withNode` place them exactly where a test needs them, `withHero` gives a hero chosen skills, `withDragon` a grown dragon of a chosen level, `reach` fulfils any quest goal, `nearCity` and `onRoad` give positions, and `runUntil` advances second by second until a condition holds.
- `server/` is the authoritative game server. The client never sends a state, only actions, and the server applies them with the rules above.
  - `app.ts` builds the Hono app and its JSON routes, listed at the top of the file: accounts, sessions, `GET`/`POST`/`DELETE /api/game` and `POST /api/game/actions`. It also serves `dist/` with cache headers. `GET /api/game` returns the game as it was at the last visit and saves it advanced to now, so the client can build the "Bon retour" summary. A request that changes a game loads, applies and saves with no `await` in between, so concurrent requests cannot interleave. Keep it that way.
  - `auth.ts` checks names and passwords and handles tokens. Names are 3 to 20 letters, digits, spaces, hyphens or apostrophes, unique regardless of case (`nameKey`). Passwords need at least 8 characters and are stored as scrypt hashes with OWASP settings. Session tokens are random, stored only as SHA-256 hashes, sent as `Authorization: Bearer`, and expire after 30 days unused. After 10 wrong passwords for a name, `app.ts` locks that name for 15 minutes (in memory).
  - `db.ts` wraps `node:sqlite` with three tables: `accounts`, `sessions`, and `games` (the state as JSON). A schema change goes in a new entry at the end of `MIGRATIONS`, tracked with `PRAGMA user_version`.
  - `main.ts` starts the server from the environment variables.
  - `app.test.ts` runs the whole app in memory, with a fake clock and light scrypt settings. It sets states directly with `giveGame` instead of depending on balancing values.
- `src/ui/` is the display layer. `useGame.ts` owns the reactive state and ticks once a second.
  - A game lives either online or on the device. Online, the session is kept in `localStorage` and the server decides. Without an account, `storage.ts` saves the game under a versioned key; bump `SAVE_VERSION` on incompatible format changes.
  - Online play: each order is applied locally right away with `performAction`, then sent to the server, whose answer replaces the state. Requests go through a queue one at a time, and only the last answer in line is applied. `api.ts` wraps `fetch` and estimates the server clock (`serverNow`), which drives the timers online. The client re-syncs every minute, when the tab becomes visible again, and every 10 seconds while the server is unreachable.
  - `away.ts` builds the "Bon retour" summary: finished work, battles, sieges (repelled or plundered, with what was taken), armies back home, hero levels, spells that ended, an objective reached, new bands and nodes, and a raid marching on (or besieging) the city.
  - Screens:
    - `AccountView.vue`: log in, create an account, or "Jouer sans compte".
    - `RaceChoice.vue`: pick a race.
    - `GameScreen.vue`: the game itself, a full-viewport screen designed for landscape, like a mobile game. It also works upright (the panel then sits under the map, and a chip suggests turning the phone). The map fills the screen: `CityMap` or `WorldMap`, kept alive so each keeps its pan and zoom. On top of it, a HUD: the resource bar, the current objective (one tap claims a reached objective), the raid alert (`raidAlert`: the countdown to the next raid's arrival, which opens that raid's panel, or "Cité assiégée", which opens the walls), what is in progress in the city (each chip opens its building), the armies outside, the city/surroundings toggle, and the Héros, Rapports and Menu buttons. Touching anything on a map opens its panel beside the map (`SidePanel`; `screen.ts` holds the `Panel` and `CitySelection` types):
      - a building: `BuildingCard`, plus `TrainingList` for the Caserne (the four family units and the player's race unit, as `UnitCard`s with a `CountPicker` slider), `ResearchPanel` and `TechCard` for the Académie, `SpellList` for the Tour des mages, `DefenseCard` for the Remparts (siege in progress, guards, health bonus, troops at home, what the Château protects, raids on the way and the next one);
      - the garrison (`GarrisonCard`: troops at rest, upkeep, famine, dismissal) and the heroes (`HeroPanel`, `HeroCard`: recruit, XP, skill points), which both have a spot on the city map;
      - a camp, a band (or a raid: its arrival countdown and an "Intercepter" button) or a node: `TargetCard`, which composes a new army (hero chips and sliders; by default every troop, led by a free hero, a gatherer for a node and a fighter otherwise) that leaves at once, or sends an army already outside, and warns about monsters near the route;
      - one of your armies: `ArmyCard` (status, battle in progress, load, hero). While an army is selected, a tap on the ground, a target or the city orders it there at once, with no button to validate: `command` checks with `checkOrder` and shows a refusal as a toast. Dragging an army to a place or a target does the same (`WorldMap` emits `command`). A fighting army only retreats through its button, so a stray tap cannot pull it out of a battle;
      - pages: the objective (`QuestBanner`), battle reports (`ReportsPanel`, with the collapsible combat log; reports show the hero's XP, and a siege report its defenders, guards lost, healed troops, and loot or plunder) and the menu (account, fullscreen with a landscape lock where the browser allows it, restart).
      "Bon retour" is a dialog over the game. `world.ts` holds the `Selection` type, the French texts for orders and army statuses, band names (`bandName`), the raids on the way (`incomingRaids`), and what animates a battle (`fightFx`: each side's health ratio and the last round's damage; `shot`: a spark's path); `battleLog.ts` holds the combat log's text and names foes (`foeName`, `bandLabel`) and outcomes (`OUTCOME_NAMES`, and `reportTitle`, which names siege outcomes from the city's side).
  - Shared pieces: `NoticeBar.vue` shows a lost connection or a refused order, and `AccountLine.vue` offers logout or going online.
  - Build settings: `VITE_LOCAL_ONLY=true` builds a game without online play, for the claude.ai demo, which cannot reach a server. `VITE_SERVER_URL` points the client at a server on another origin; the Android app will need it later, along with CORS on the server.
- Maps are plain SVG, no library. `MapViewport.vue` fills its frame and handles panning and zooming (pointer events for drag and pinch, wheel, keyboard, on-screen buttons that `GameScreen` places through CSS variables); one can zoom out until the whole map shows. It renders its slot in world units. A tap only counts as a selection when the pointer did not drag; a tap on the background emits `tap` with the point in world units. It exposes `centerOn` (the maps center on each new selection, once the panel has opened, and also when a map first appears with a selection already made: a point asked for before the map has a size waits until it is framed) and `toWorld` (used to drag armies). `maps.ts` holds the city layout (building plots, the garrison and heroes spots, the wall, and `CITY_SIEGE`, where besiegers stand) and the deterministic decor; positions on the world map come from `config.ts`. `CityMap.vue` and `WorldMap.vue` draw the scenes; bands and armies move once a second, smoothed by a CSS transition (`.mover`). On the city map, the wall is a palisade until the Remparts are built, then a stone wall that thickens with their level, ringed in red during a siege. On the world map, a raid has no patrol loop but a red path to the city, and a raid at the gates is drawn in front of the city, on the side it came from (`drawnPosition`), so it never hides the city. A fighting army is drawn beside its foe, at the same height and `FIGHT_GAP` away (`apart`, `foePosition`), so their labels and health bars never overlap.
- Battles are animated on both maps: a `HealthBar` above each side (gold for the player, red for monsters), the damage of each round floating up (`.float-damage`), a shake on whoever is hit (`.hit`), sparks flying between the fighters (`.spark`) and crossed swords that bump each round, with the round number in a badge. Elements keyed by the round number restart their CSS animation each round. During a siege, both bars and both damage numbers sit above the besiegers on the city map.
- The maps have some life: `MapGround` draws the ground (terrain patches from `maps.ts` and a grass pattern); mountains have snow caps (`mountainSnow`) and, like trees, a shadow; roads have edges; water flows (`.river-light`, in steps to spare phones) and the lake shimmers; campfires flicker by the camps; marching armies and bands bob (`.walker`), gatherers swing their pickaxe, raids pulse; in the city, the hammer of a works hits, producing buildings release their resource now and then (`.puff`), the mana well glows, and the Caserne, Académie and Tour des mages show when they are busy. `MapViewport` adds drifting clouds and a vignette as HTML layers over the map, which cost little. The selected spot's ring breathes. A global `prefers-reduced-motion` rule in `style.css` stops all of it.
- Styling: a single dark theme defined as CSS custom properties in `src/style.css`, which also holds the shared card (`.plaque`), grid, progress and form styles; component styles are scoped. The game screen takes the full height (`html`, `body` and `#app` are 100 % high, with the phone's safe areas as padding on `:root`), while the account and race screens scroll. Lists of cards (`.grid`) follow the width of their panel through a container query. Icons are emoji placeholders set in `config.ts`. `docs/graphismes.md` holds the art style guide and the list of images (with file names) that will replace them.

## Game Design

Design decisions live in `docs/conception.md` (in French). It is the source of truth and supersedes the README where they differ. Read it before implementing gameplay, and update it whenever the owner settles a design question. Each item is tagged Décidé, Proposition or À trancher.

In short: a free-for-everyone (no pay-to-win) multiplayer kingdom-building strategy game, in the same genre as Rise of Kingdoms but with a medieval-fantasy setting (several playable races, magic, dragons). Everything runs in real time with durations, combat included: there is no turn-based mode. Progress continues while the player is offline. All content (name, races, heroes, art) must be original; never reuse Rise of Kingdoms' content.

Platform roadmap: web app first, then packaged as an Android app via Ionic/Capacitor. Keep the web stack compatible with that (the Vite build already uses relative asset paths). The game is played in landscape: the Android app will lock that orientation (`android:screenOrientation="sensorLandscape"`).

## Working with the Owner

The project owner communicates in French and is learning to code. Respond in French, explain technical choices simply, and prefer incremental steps over large opaque changes.
